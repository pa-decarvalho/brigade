# Development

Working on brigade itself. Requires [mise](https://mise.jdx.dev/) and, for `ci:test`, a running Docker.

```sh
mise trust && mise install
mise run brigade:hooks    # optional: lint before each commit
mise run lint
mise run build            # the documentation site, strict
mise run test
mise run zensical:serve   # preview the site
```

## Repository

- `copier.yml` includes `.copier/settings.yml` and `.copier/questions/`: `common.yml`, then one file per tool in `tools/`.
- `template/` holds the generated files.
- `ctt.toml` lists the test variants.
- `docs/` and `zensical.toml` hold this site.

brigade is generated by brigade: `.mise/` and the `.github/` CI files come from the latest release, with the answers in `.mise/brigade-copier-answers.yml` (lint commands adapted to `template/` and `.ctt/`, `ctt:test` clearing `.ctt/` first). `mise run brigade:update` updates them after a release. brigade's own tasks (`update:test`, `ci:test`) live in `.mise/conf.d/project.toml`.

## Lint

`mise run lint` checks this repo: yamllint, actionlint, taplo, editorconfig-checker, gitleaks, typos and the Renovate config schema.

## Tests

`mise run test` runs:

- `ctt:test`: renders each `ctt.toml` variant into `.ctt/` with [ctt](https://github.com/KyleKing/copier-template-tester), creates a real project there with the ecosystem's tool, then runs its stages. ctt only sees files tracked by git: `git add` new template files before testing.
- `update:test`: for each variant, applies the latest release, updates to the current commit with `mise run brigade:update`, then runs the stages.
- `ci:test`: runs each variant's generated CI locally with its `brigade:ci-local` task: [act](https://github.com/nektos/act) (GitHub, Gitea) or [gitlab-ci-local](https://github.com/firecow/gitlab-ci-local) (GitLab). It needs Docker; Docker Desktop's socket is found on macOS.

brigade's CI runs these tests on Linux only.

`mise run build` builds this site in strict mode, which fails on broken links. CI deploys it (`pages:deploy`, to the `gh-pages` branch) on a manual run of the CI workflow: release tags made with the workflow token start no CI.

## Versions and releases

Pinned versions are updated by [Renovate](https://docs.renovatebot.com/) (`.github/renovate.json5`), run every Monday by `.github/workflows/renovate.yml` as one PR, `fix(deps): update template`, major updates included: it triggers a release.

Renovate only reads `template/`. brigade's generated files get the new versions like any project, through a release and `mise run brigade:update`; its other pins (`renovate.yml`, Copier and pytest in `ctt.toml`, `README.md`, `.mise/scripts/` and `.copier/settings.yml`) are updated by hand.

It needs a `RENOVATE_TOKEN` secret: a fine-grained token on this repo with contents, pull requests, issues, workflows and commit statuses read/write.

Commits and PR titles follow Conventional Commits. On each push to `main`, the CI's `release` job runs [Releasaurus](https://github.com/robgonnella/releasaurus) (`mise run release`): it opens or updates the release PR, and once merged tags `X.Y.Z` and updates `CHANGELOG.md`; Copier uses these tags as template versions. `releasaurus.toml` makes a release on `feat`, `fix`, `perf`, `revert` and breaking changes only: other commits do not change the template.

It uses the workflow token: the release PR and the tag start no CI, so the release PR is merged with a bypass of the required checks, and the site is deployed by a manual run of the CI workflow.
