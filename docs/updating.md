# Updating

*Fresh deliveries: a new brigade release, straight to your kitchen.*

```sh
mise run brigade:update
```

This runs `copier update` with the answers in `.brigade/copier/answers.yml` (edited in `.brigade/copier/data.yml`, see [Changing answers](questions.md#changing-answers)) and applies the latest brigade release: new tool versions, new tasks, CI changes.
Commit your work first: Copier needs a clean git tree, and shows conflicts as inline markers.

With the `renovate` tool, Renovate opens this update as a PR on each release (see [brigade updates](tools.md#brigade-updates)); with the `brigade` tool, `brigade:lint` tells when a release is out.

brigade releases are tagged `X.Y.Z`. Tool versions are bumped by Renovate in brigade, so a project gets them through a release and `brigade:update`.

## Lockfile

`.brigade/mise.lock` holds the exact version of each brigade tool, with the URL and checksum of its download for Linux, macOS and Windows; `.brigade/.mise/locks/` holds the Python and npm dependencies of the `pipx:` and `npm:` tools. `brigade:update` writes them after each update (`mise -C .brigade lock`; from the root, `mise lock` only locks your `mise.toml` when you have one): commit them with it. Then `mise install`, locally and in CI, installs these versions and fails when a download does not match its checksum (a release republished under the same version). Without a lockfile, it installs the pinned versions without checksums.

A failed `mise lock` (offline...) does not fail the update: run `mise -C .brigade lock` again. The tools you add in your `mise.toml` are locked with `mise lock`, in your own `mise.lock` next to it.

Tools that a task declares (`[tasks.<name>.tools]`: `npm:renovate` for `renovate:operate`) are not locked from `.brigade/` (mise 2026.11): they install as before, and `mise install` may add them to the lockfile and `.brigade/.mise/locks/` in CI.

## What is overwritten

Files generated by brigade belong to brigade: local edits show up as conflicts on update. The `brigade` tool (`brigade:lint`) catches them before: see [brigade](tools.md#brigade).

Files you add are yours: brigade never touches them, such as `mise.toml`, your own workflows or `.gitlab/ci/*.yml` files.

See [CI platforms](ci.md). For your own tasks, see [Custom tasks](custom-tasks.md).

## From brigade 0.23 and earlier

Since 0.24, the tool files are in `.brigade/conf.d/` (was `.brigade/tools/`), so that mise writes one lockfile for them all. Update as usual: Copier moves them. This first update runs the previous `brigade:update`, which does not lock: then run `mise -C .brigade lock` (mise may ask you to trust the moved files: `mise trust`), and commit the update with `.brigade/mise.lock` and `.brigade/.mise/`.

With `yamllint` and an `npm:` tool (renovate, cspell, markdownlint...), add `.mise/` to `ignore` in `.brigade/configs/yamllint.yml` (yours, so not updated): `.brigade/.mise/locks/` holds their dependency graphs as YAML.

## From brigade 0.12 and earlier

Since 0.13, the answers are in `.brigade/copier/`. Update as usual (or merge Renovate's PR), then move them:

```sh
mise run brigade:update
git mv .brigade/answers.yml .brigade/copier/answers.yml
git commit -m "chore: move brigade answers"
```

Until then, `brigade:lint` fails and `brigade:update` cannot find the answers.

## From brigade 0.5 and earlier

Before 0.6, brigade's files were in `.mise/` and `.github/actions/` (`.gitea/actions/`, `.gitlab/ci/`). Move your answers, then update:

```sh
mkdir -p .brigade/copier
git mv .mise/brigade-copier-answers.yml .brigade/copier/answers.yml
git commit -m "chore: move brigade answers"
uvx copier@9.19.1 update -a .brigade/copier/answers.yml
```

Copier removes the old generated files. Move your own files out of `.mise/` into `mise.toml` (see [Custom tasks](custom-tasks.md)): mise no longer reads `.mise/`.
